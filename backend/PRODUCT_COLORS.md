# Product colours — Phase 1 backend contract

## Deployment gate

`20261109180000_product_colors` is a new additive migration. It has **not** been
applied to Neon or the application's configured database. Run migration tests
only against a fresh local PostgreSQL cluster. Do not deploy the new generated
client/backend against the old schema before the reviewed migration is applied.
No existing migration should be edited or replayed against an existing database.

## Data preservation

- Product colours are grouped by `(productId, exact colorName)`, not hex, legacy
  `color`, normalized casing or trimmed names.
- Each original variant gains only a nullable `colorId`. IDs, SKUs, stock,
  overrides, thresholds, activity, timestamps and inventory history stay intact.
- Blank/case/spacing colour names remain distinct legacy groups. New explicit
  colours require a nonempty trimmed name.
- A group's hex is copied only when every original variant has the same valid
  hex. Conflicting/blank hex becomes `null`; original variant swatches remain.
- Existing image rows gain nullable `colorId` and remain in the shared gallery.
  URLs, public IDs, ordering, primary/activity flags and timestamps are preserved.
- Composite foreign keys prevent cross-product colour references. The original
  size/name uniqueness remains, with additional `(colorId, size)` uniqueness.
- Nullable variant references support additive rollout/older writers. New APIs
  always establish a colour; a later reviewed contract migration can make this
  required once all writers have upgraded.

## Read compatibility

`GET /api/v1/products` and `GET /api/v1/products/:id-or-slug` retain the flat
`images`, `variants`, `image`, `price` and `stock` fields, variant colour aliases,
and effective prices. Admin reads retain inactive rows. Public reads exclude
inactive colours and their variants/images without changing child records.

Additional fields:

- `colors[]`: `id`, `productId`, `name`, `hex`, `sortOrder`, `isActive`, timestamps,
  its own `images[]`, `variants[]`, `image` and `usesSharedGallery`.
- `sharedImages[]`: only product images with `colorId: null`.
- Flat images/variants also carry their nullable `colorId`.

An empty colour gallery uses the shared cover via `color.image` and declares
`usesSharedGallery: true`; its `images` array remains empty so clients can decide
whether to use the full shared gallery. Product cover prefers the shared primary,
then the first active colour's cover. Image ordering never changes merely because
an image is primary. Multiple primary flags in the flat array are expected: each
nonempty gallery has its own primary.

Product queries also accept `colorId` alongside the existing size/name filters.
Stock/effective-price fields continue to refer to exact size variants, not pooled
colour inventory. Inactive colour stock is retained but excluded from active
inventory/dashboard totals, and adjustments are blocked until the colour is
reactivated.

## Colour and variant writes

Admin routes use the existing authentication/ADMIN gate:

- `POST /api/v1/admin/products/:id/colors`: `{ name, hex?, sortOrder?, isActive? }`
- `PATCH /api/v1/admin/products/:id/colors/:colorId`: the same optional metadata,
  plus optional `expectedUpdatedAt` for optimistic concurrency.
- `DELETE /api/v1/admin/products/:id/colors/:colorId`: JSON
  `{ expectedUpdatedAt: "original ISO-8601 revision" }`. Soft-deactivates only.

Explicit name/hex edits synchronize current variant compatibility fields while
preserving SKU, stock, price overrides, thresholds and movement/order snapshots.
Colour deactivation does not erase images, deactivate/recreate variants, reassign
stock or call Cloudinary. Reactivation restores the colour without restoring
individually deactivated variants.

Existing variant POST/PATCH routes accept `colorId`; legacy colour-name input
still resolves/creates a colour by exact name. Explicit ID plus contradictory
colour metadata is rejected on association. Repeating the current colour ID does
not reassign the variant or erase a retained conflicting swatch. Existing option
strings on PATCH remain exact, including legacy whitespace and invalid swatches;
new/changed swatches still require `#RRGGBB` or empty. Sizes remain free-text;
only supplied combinations are created. SKU input remains compatible with existing
automatic admin generation; existing SKUs are never regenerated by a migration/colour edit.

Any changed variant metadata or activation requires its **original**
`expectedUpdatedAt`; stale or missing revision returns 409. Unchanged legacy
metadata on an already-linked variant can round-trip without a revision and does
not advance timestamps. Nullable older-writer rows establish their colour link
on update while retaining their original swatch. This
prevents a stale drawer's unconditional metadata PATCH from undoing a concurrent
colour rename, price override, size/SKU or threshold edit. Deactivation separately
requires a revision even when already inactive (missing token is 400).

Product creation accepts the old flat arrays or optional nested `colors`:

```json
{
  "sku": "SHIRT-001",
  "name": "Oversized Gym T-shirt",
  "slug": "oversized-shirt-001",
  "categoryId": "category-id",
  "priceCents": 3000,
  "colors": [
    {
      "name": "White",
      "hex": "#FFFFFF",
      "images": [{ "url": "https://example.invalid/white-front.jpg", "isPrimary": true }],
      "variants": [{ "sku": "SHIRT-001-WHITE-S", "size": "S", "stock": 10 }]
    }
  ]
}
```

Nested rows inherit their colour. No missing size combinations are generated.
Initial stock is allowed only on **new** variants and receives an audited receipt.
Ordinary product PATCH is scalar-only; child arrays/stock are rejected. Variant
PATCH rejects stock. Dedicated inventory adjustments remain independently audited.

## Image/gallery writes

Colour-scoped routes:

- `POST /admin/products/:id/colors/:colorId/images`
- `PATCH /admin/products/:id/colors/:colorId/images/:imageId`
- `DELETE /admin/products/:id/colors/:colorId/images/:imageId`
- `PATCH /admin/products/:id/colors/:colorId/images/reorder`: `{ imageIds }`

URLs and authenticated multipart/binary uploads retain the existing validations,
5 MiB/file limit and 30 active images/product policy. Image IDs must belong to the
specified product/colour. Primary selection, append ordering, reordering and
replacement-primary fallback affect only that gallery.

Existing product image routes remain. POST without `colorId` creates a shared
image; PATCH/DELETE by image ID operate in its existing gallery. An explicit
product-image PATCH `{ colorId: "target-id" }` (or `null`) moves an image without
re-uploading/deleting assets, preserving its ID, URL and public ID. Both galleries'
primaries are normalized; implicit moves from colour-specific routes are rejected.

Reorder accepts `{ imageIds, colorId }` on the product route. An omitted scope
retains the old shared-gallery behavior until coloured images exist; then it
returns 409 instead of mixing independently ordered galleries. Explicit
`colorId: null` continues to reorder the shared gallery. Every gallery's complete
active image-ID set is required exactly once.

Cloudinary upload remains outside retryable DB transactions. Public IDs are
server-owned and never client-accepted. Every replacement, including an unmanaged
external URL, creates an inactive historical copy in the original gallery and
returns its `previousImageId`. Removal keeps the original row. Cleanup only runs
after checking every other image, legacy, category and historical-order reference,
including references across colour galleries. Unmanaged URLs are never sent for
Cloudinary deletion.

## Safety changes for the unchanged frontend

The old admin hook has unsafe behaviors that cannot be made intentional by
silently reinterpreting its requests. Backend gates fail closed until Phase 2:

1. Variant deactivation (DELETE or PATCH `isActive: false`) requires the variant's
   **original** `expectedUpdatedAt`. Missing token is 400; changed token is 409.
   A scalar product save never infers deletion from absent rows. The old drawer's
   unqualified deletes can no longer deactivate concurrently added variants.
2. The old hook's automatic inventory request with reason
   `Stock edited from the admin product form` returns 409. A stale product draft
   can no longer overwrite current stock through that legacy save path. Genuine
   explicit inventory adjustments continue with their own reason/count and
   existing expected-stock checks.
3. Changed variant metadata/activation without an original revision returns 409;
   unchanged exact metadata remains a no-op. An ordinary legacy drawer save cannot
   silently undo a concurrent colour rename or overwrite variant overrides/thresholds.

These are intentional compatibility exceptions, not a claim that the old drawer
has been corrected. Phase 2 must remove stock synchronization from product saves,
provide a separate explicit inventory action, track original revisions/removal
intent, and handle colour-scoped image operations. Until then variant-edit,
stock-edit and variant-remove saves may report partial-save errors rather than
applying unsafe changes.

## Verification

Migration regression snapshots every original column/row before/after backfill,
including Cloudinary handles, carts, orders and inventory movements. Endpoint
regressions cover unequal size sets, independent galleries/primaries, ownership,
compatibility aliases, deactivation revisions and inventory isolation. Cloudinary
is mocked only at the provider boundary; no live asset operation is needed.

The isolated test runner creates a fresh local PostgreSQL cluster, overrides all
database URLs and Cloudinary configuration, applies migrations there, checks
schema drift and runs endpoint/migration tests. It never resets the application
or uses a configured Neon URL. Test cluster logs/data are retained locally.
